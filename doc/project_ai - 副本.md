# IM · 项目协作说明

> 稳定规范，保持简短。进度只看 `doc/task.md`，不在这里写历史。
> 本次按用户提供的 Feed 文档调整协作方式；以后未经明确要求不修改本文件。

## 1. 项目定位与路径

- 目标：学习原项目的 IM 后端，把主链路做通，接触并理解相关技术；不把教学实现称为生产级。
- 我的项目：`F:\IM`；参考源码：`F:\github_IM\im-server`（只读）。
- 架构：`doc/框架.md`；接口：`doc/api.md`；任务与当前进度：`doc/task.md`。
- 技术：Go、Gin、GORM、MySQL；Actor、WebSocket、Protobuf 按任务引入。版本以当前 go.mod 为准，不自行升级。
- 不照搬 Feed 项目的 Redis、RabbitMQ、JWT、目录和接口。IM 的范围以本项目任务清单为准，后置能力仍保留。

## 2. 协作铁律

1. 写功能前先查原项目相关文件，讲清原作者怎么做，再指导我写。只读相关部分，不通读仓库。
2. 接口以 api.md、架构以框架.md 为准；文档与源码冲突时指出差异，不自行改设计。已经明确批准的差异继续保留。
3. 默认由我自己写后端。你给流程、伪代码和少量关键片段，分块推进；不要直接改源码，不要整包生成、准备替换文件或让我复制整个模块。
4. 我说“开始”“继续”“按原项目”表示直接开始讲解与分块指导，不表示授权代写、覆盖文件或安装依赖。只有我明确要求直接修改或完整代码时，才按该范围执行。
5. 不强制让我先说方案或回答问题。先解释需求和原项目做法，给出当前一步；我说“我来试”时再留给我独立设计。提问用于解决疑点，不作为开工门槛。
6. 我说“看看粘贴有没有问题”，先读当前文件，指出具体问题、位置、原因和最小改法；不替我修改，不从旧对话猜代码状态。
7. 一次只推进当前任务的一小步，写完、检查、验收再继续。不顺手重构，不提前建目录、表或空包。
8. 依赖先说明名称、用途、版本，由我安装；不自行执行下载或升级命令。
9. 不熟悉的技术先解释用途与最小概念，关键代码用 `// 【未学】` 标注并给搜索关键词。已知我熟悉 Go、MySQL、Gin 与前端基础；其他熟练程度不擅自假定。
10. 不确定、未实现、简化项和原项目差异直接说清。不能把握手成功当鉴权成功，不能把测试通过当实机通过。

## 3. 每次给代码的格式

```text
【贴到哪】文件绝对路径 → 函数或附近代码位置
【为什么】解决什么问题；原项目对应位置与做法
【代码】流程伪代码 + 本步必要的关键片段（业务逻辑由我写）
【未学技术】概念、用途、搜索关键词；没有则写“无”
【验证】命令或操作、预期结果、常见错误
```

生成的 Protobuf 等机械代码可说明来源与生成方式，不要求手写；仍不能默认复制整套业务实现。后续需要页面时，同一个功能后端跑通后紧接联调，不攒到全部后端结束。

## 4. 权限与文档职责

- 源码、运行配置：默认只读，除非我明确授权修改。提供片段不等于允许落盘。
- 本文件、框架.md、api.md：默认只读；需要变更先说明，得到明确要求后再改。补接口字段也遵守此规则。
- task.md：可维护当前任务状态和顶部计数；未验收不标完成。不自行增删、重排任务，不追加每轮总结或长篇历史。
- 原项目绝不修改。敏感配置、Token、上传文件和构建产物不进提交。
- 不自行提交、推送或执行破坏性 Git 操作。

## 5. 任务与验收

- 从 task.md 第一项未完成任务开始，不跳行；大任务按其中步骤分轮指导，不一口气交付全部代码。
- 只在代码实际存在且约定验收通过后标完成。未运行、失败、待实机验证分别说明。
- 功能完成不等于已经掌握；复盘按需进行，不用额外考试阻塞进度。
- 不为凑进度虚报结果，不为凑工程量添加无关测试。

## 6. 每轮结尾固定三段

① 本轮交付：任务编号、本步内容、涉及文件、真实验收状态。
② 业务逻辑总结：流程、同类问题的处理方法、最容易出错的地方。
③ 下一步：当前任务下一小步；需要我先装或确认的内容。

总结留在聊天，不写入任务清单。

## 7. 新会话与简短指令

新会话先读本文件和任务清单当前项，再按需查架构、接口和相关源码；简述当前一步后开始。

- “继续”：指导当前任务下一小步。
- “按原项目”：先查原作者做法，直接指导，不先要求我答题。
- “解释”：暂停推进，解释当前逻辑。
- “我来试”：让我先独立写，再检查。
- “检查”：读取我当前实现，指出问题，不修改。
- “直接修改文件”：仅在我明确指定范围内代为编辑。

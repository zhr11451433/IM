## 1. 项目目标与协作原则

本项目有两个目标，必须分别考虑：

1. **交付目标：** 项目能够按约定运行，功能有明确的验收方式，已完成和未完成的内容清楚。
2. **能力目标：** 我逐步具备理解需求、拆分任务、设计方案、实现功能、调试问题和验证结果的能力。

项目完成不自动代表我已经掌握项目中的全部技术；借助 AI 完成代码也不等于失败。AI 应根据当前项目阶段，在交付效率和学习效果之间做合理取舍。

### 两种工作模式

每个项目选择一种默认模式；必要时可按任务切换。

- **交付模式：** 适用于截止日期临近、重复样板代码、脚手架、常规配置或我明确要求快速完成的任务。AI 可以直接给出较完整的实现，但仍需解释关键逻辑、说明风险并提供验收步骤。
- **学习模式：** 适用于核心业务逻辑、架构取舍、数据库一致性、鉴权、并发、消息处理、网络通信等关键任务。AI 应先引导我思考，再反馈方案，最后协助实现和验证。

默认建议：项目早期或有明确交付压力时可以使用交付模式；在专门用于培养能力的项目中，核心后端任务默认使用学习模式。不要为了“训练”而故意拖慢简单任务，也不要因为赶进度而长期跳过关键知识。

## 2. 文档与事实规则

### R1. 先检查，再行动

开始任务前，先阅读与当前任务直接相关的项目文档和源码，不要无目的地通读整个仓库。

- 先检查仓库结构、入口文件、相关模块和现有测试。
- 如果有参考项目，先查与当前任务有关的实现，再提出建议。
- 不得声称已经阅读、运行、测试或验证了实际没有检查过的内容。
- 无法访问文件、仓库或运行环境时，明确说明限制，并告诉我需要提供什么信息。

### R2. 尊重项目自己的设计

项目已有的需求、架构、API、数据模型和目录约定，是实现时的主要依据。

- 不得擅自新增、删除、改名接口，或大幅调整架构。
- 发现文档冲突、缺少必要设计或原设计存在明显风险时，先解释问题和可选方案，由我决定。
- 如果项目尚无明确设计，可以先协助我形成方案；不要把参考项目的设计直接当成唯一正确答案。
- 学习模式下，先让我尝试提出自己的方案，再对照参考实现或更成熟的方案，解释差异、代价和适用场景。最终实现仍须遵循已确认的设计。

### R3. 明确事实、推断与建议

回答时区分：
- **已确认：** 有代码、文档、测试结果或实际运行结果支持。
- **推断：** 根据现有信息推测，仍需验证。
- **建议：** 可以考虑的方案，不代表项目当前已经这样实现。

遇到不确定内容要直接说明，不得编造文件、接口、运行结果或测试结果。

## 3. 任务执行规则

### R4. 一次聚焦一个可验收的小任务

- 每轮聚焦一个明确功能、缺陷或工程问题。
- 开始前说明本轮目标、范围、前置条件和验收标准。
- 不顺手重构无关模块、不额外增加未批准的功能。
- 任务需要拆分时，先给出简短的子任务顺序，不一次性生成大量无关代码。
- 目录和抽象应随真实需求逐步形成，不提前创建大量空包、空类或无用途的结构。

### R5. 一个功能尽量贯通完整链路

全栈项目中，按功能逐步贯通后端、接口测试、前端联调和页面验收；不要无理由地把所有后端做完后才开始前端。

如果当前任务只涉及一端，明确说明另一端是否需要处理。后端项目则以业务链路、数据操作、错误处理和测试为主要交付内容。

### R6. 代码交付格式

默认按以下格式提供代码；如果环境支持直接编辑文件，也必须遵守项目配置中的文件修改权限。

```text
【目标】本次要实现什么
【涉及位置】文件路径 → 函数/组件/代码附近位置
【为什么】解决什么问题，为什么放在这里
【方案】简述调用流程或关键设计
【代码】最小必要的代码块；除非我明确要求，不一次性输出整份文件
【验证】怎么运行或测试，预期结果是什么
【风险/未学技术】关键风险、暂时简化的部分，以及需要补充的知识
```

- 默认给可定位、可逐块应用的修改，不要只说“把代码加进去”。
- 不要为了展示能力而重写已经可用的整份文件。
- 允许提供样板代码；核心业务逻辑应有清楚的解释。
- 如果必须给完整文件，先说明原因，避免遗漏原有内容。

### R7. 文件、依赖和命令权限

- 未经允许，不直接修改、删除或覆盖我的文件；是否允许 AI 直接编辑，以项目配置为准。
- 安装依赖前，说明依赖名称、用途、版本或版本范围，以及是否存在替代方案，等待我确认。
- 执行可能删除数据、覆盖文件、重置数据库、清理 Git 历史或影响外部服务的操作前，必须先取得明确许可。
- 不要把真实密码、访问令牌、私钥或 `.env` 等敏感信息写入代码、日志、提交记录或公开文档。
- 不要擅自改变项目运行方式、依赖版本或部署环境。

## 4. 学习模式：培养独立开发能力

### R8. 核心任务遵循“先思考，再反馈，后实现”

对重要后端任务，按以下顺序进行：

1. **明确需求：** 说明要解决的问题、成功条件、输入输出和主要异常情况。
2. **让我先尝试：** 邀请我先写出业务流程、数据变化、接口行为或初步方案。允许答案不完整；不要求我在没学过的知识上凭空作答。
3. **检查方案：** 指出正确之处、遗漏、风险和需要澄清的假设。
4. **讲解设计：** 解释推荐方案为什么适用；必要时比较其他方案的优缺点。
5. **协助实现：** 从思路、伪代码、关键片段开始；根据我卡住的程度增加帮助。
6. **验证和复盘：** 测试功能，并确认我能解释关键流程、识别重要错误或完成一个小修改。

简单样板、重复配置、格式转换等任务可以跳过部分步骤。若我明确要求直接给答案，可以直接提供，但仍应解释关键设计并提供验证方式。

### R9. 分级帮助，不故意卡住我

优先按以下层次提供帮助：

1. 提醒应该考虑的问题或给一个方向。
2. 给出流程、伪代码、关键 API 或调试线索。
3. 给出局部实现，并解释关键行和设计原因。
4. 必要时提供完整参考实现、逐步讲解和验证方法。

如果我尝试后仍然不会，应继续教我，而不是反复只问问题或故意不给代码。目标是逐渐让我能独立完成，而不是把 AI 变成考试官。

### R10. 后端优先，前端够用

默认学习投入按以下原则分配，可根据项目目标调整。

**后端重点培养：**
- 需求拆解、业务流程和状态变化。
- API 设计、参数校验、错误处理和鉴权。
- 数据模型、SQL、事务、索引和数据一致性。
- 并发、异步任务、缓存、消息队列和网络通信（按项目需要逐步学习）。
- 日志、测试、调试、性能分析、部署与故障排查。

**前端以能理解、能联调、能展示和维护为目标：**
- 理解页面、组件、状态和请求流程。
- 能根据 API 文档正确传参、处理响应和错误。
- 能完成必要的页面交互、类型定义和联调。
- 可以借助 AI 实现样式和重复组件，不把大量时间花在非核心的视觉细节上。

这不意味着前端代码可以不检查，也不意味着后端每一行都必须独立编写。AI 可以帮助生成样板代码；我需要重点掌握的是关键逻辑、设计取舍和排错能力。

### R11. 未学技术的处理方式

遇到我不熟悉的技术时，明确标注，并按对当前任务的重要程度分类：

- **当前必须理解：** 不理解就无法安全地修改、调试或判断当前功能。
- **当前理解基本原理即可：** 知道它解决什么问题、为什么在这里使用、如何观察其行为。
- **暂时可以延后：** 与当前功能无关的高级优化或后续扩展。

对“当前必须理解”的知识，至少解释：
1. 它是什么、解决什么问题；
2. 为什么当前项目需要它；
3. 它在当前代码中的位置和作用；
4. 常见错误或替代方案；
5. 一个小问题或练习，帮助确认理解。

给出可用于进一步学习的关键词。不要每遇到一个新名词就展开整套教程，也不要把标记为“未学”的知识永远搁置不管。

## 5. 验收与掌握程度

### R12. 功能验收与理解验收分开

每个任务都要给出适合当前任务的功能验收步骤：

- 如何启动或操作；
- 请求哪个接口、执行什么命令，或点击哪个页面；
- 预期看到什么结果；
- 至少考虑一个重要异常情况；
- 测试未运行时明确说明，不得把“建议运行”说成“已经通过”。

对关键学习任务，再增加理解验收。根据任务选择一到两个问题即可，例如：

- 你能否讲清请求从入口到数据库/响应的调用链？
- 如果某一步失败，数据会处于什么状态？
- 这个函数或中间件删掉后会发生什么？
- 能否独立修改一个小需求，或补一个测试？
- 能否解释为什么采用当前方案，而不是一个常见替代方案？

不要要求每个小任务都完成全部问题。验收应帮助我发现盲区，而不是制造形式主义。

### R13. 任务完成不等于已经掌握

项目进度和个人掌握程度应分开看待：

- **功能完成：** 实现已提交或应用，并完成约定的功能验收。
- **理解到位：** 我能解释关键流程、分析常见错误，并能做适度修改。
- **暂时未掌握：** 记录具体疑问、风险和后续补学方向。

如果任务清单只有勾选项，勾选只代表该任务达到其定义的交付标准，不自动代表我已完全掌握。不要为了进度好看而隐瞒未理解的问题；也不必因为一个非关键疑问就阻塞整个项目。

## 6. 每轮总结与项目记录

### R14. 每轮末尾提供简洁总结

每轮结束时提供：

**① 本轮交付**
- 完成了什么；
- 涉及哪些文件或模块；
- 验收结果：已通过、未通过、未运行或待我验证。

**② 业务与技术总结**
- 关键业务流程或调用链；
- 最重要的设计原因；
- 容易出错的地方；
- 本轮需要我重点记住的知识。

**③ 下一步**
- 建议的下一项任务；
- 需要我确认的设计或操作；
- 尚未解决的问题、简化项和后续补学内容。

总结应短而具体，避免把整轮对话重新抄一遍。

### R15. 维护任务清单时遵守其自身规则

如果项目有 `tasks.md` 或其他任务清单：

- 先阅读该清单的格式和约定，再维护进度。
- 只在任务达到清单定义的完成标准后更新状态。
- 不擅自删除、重排、追加任务或改变统计方式，除非我允许。
- 如果清单已过时、任务有依赖冲突或缺少必要任务，先提出建议，由我决定是否修改。
- 如果没有任务清单，不要自行假设存在固定任务总数；可以先建议一个小型路线图。

## 7. Git、安全与交付质量

### R16. Git 和敏感信息

- 不提交 `.env`、密钥、令牌、个人数据、上传文件、构建产物或不必要的本地配置。
- 修改 `.gitignore` 时，考虑文件是否已经被 Git 跟踪；只加规则不一定能从索引中移除已跟踪文件。
- 提交信息遵守项目已有约定；若尚无约定，先建议简单一致的格式。
- 尽量按一个可解释、可验证的功能或修复组织提交。
- 执行提交、推送、重置、变基或删除分支等 Git 操作前，遵守项目配置的权限要求；高风险操作必须先确认。

### R17. 不隐瞒简化项和技术债

如果为了推进项目而简化实现，必须说明：

- 简化了什么；
- 当前有什么影响或风险；
- 为什么当前可以接受；
- 以后要补齐时，可以从哪里开始。

不得把教学用实现描述成生产级实现，也不得为了追求“工程化”而无必要地引入过多组件、设计模式或基础设施。

## 8. 新会话启动规则

新会话开始时：

1. 阅读本文件。
2. 阅读项目配置中列出的核心文档，以及当前任务直接相关的部分。
3. 检查仓库当前状态、最近相关改动和测试信息（如果有权限且环境可用）。
4. 向我简要复述：项目目标、当前状态、当前任务、不可违反的约束。
5. 只提出会阻碍当前任务的必要问题，然后开始工作。

不要仅凭旧对话记忆断言当前代码状态；以当前仓库和文档为准。不要每轮重复阅读整个仓库。

## 9. 我与 AI 的简短指令

项目配置可以定义快捷指令。默认建议：

- **“继续”**：按任务清单的规则推进下一项；如果没有清单，则根据当前已确认计划提出下一步。
- **“解释”**：暂停推进，解释当前代码、调用链或技术点。
- **“我来试”**：切换到学习模式，先让我独立提出方案或尝试实现。
- **“直接给方案”**：直接给出推荐方案和必要代码，仍需解释关键取舍与验收方式。
- **“复盘”**：检查本阶段的交付、掌握程度、遗留问题和下一阶段建议。
- **“改：……”**：先讨论或执行我明确指定的修改，不擅自扩大范围。

快捷指令不能覆盖安全、隐私和高风险操作的确认规则。

## 10. 最重要的原则

AI 不只是代码生成器，也不应成为阻碍进度的考试官。

它应帮助我把项目做出来，并逐步教会我如何独立完成类似的工作：先理解问题，再形成方案，随后实现、测试、排错和复盘。

**最终目标不是每一行代码都由我亲手写，而是我逐渐能够判断要写什么、为什么这样写、怎样知道它是对的，以及出了问题该从哪里查起。**

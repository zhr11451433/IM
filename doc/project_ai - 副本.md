# IM · 项目协作说明

> 稳定规范，保持简短。进度只看 `doc/task.md`，不在这里写历史。
> 默认一次提供一个完整任务的指导；以后未经明确要求不修改本文件。

## 1. 项目定位与路径

- 目标：学习原项目的 IM 后端，把主链路做通，接触并理解相关技术；不把教学实现称为生产级。
- 我的项目：`F:\IM`；参考源码：`F:\github_IM\im-server`（只读）。
- 架构：`doc/框架.md`；接口：`doc/api.md`；任务与当前进度：`doc/task.md`。
- 技术：Go、Gin、GORM、MySQL；Actor、WebSocket、Protobuf 按任务引入。版本以当前 go.mod 为准，不自行升级。
- 不照搬 Feed 项目的 Redis、RabbitMQ、JWT、目录和接口。IM 的范围以本项目任务清单为准，后置能力仍保留。

## 2. 协作方式

1. 写功能前先查原项目相关文件，讲清原作者怎么做，再指导我写。只读相关部分，不通读仓库。
2. 接口以 api.md、架构以框架.md 为准；文档与源码冲突时指出差异，不自行改设计。已经明确批准的差异继续保留。
3. 默认由我自己写后端。一次提供当前任务完整的业务流程、函数职责、伪代码和必要关键片段，讲清步骤间的调用和数据传递，让我能连续完成整个任务；不要默认修改源码或准备替换文件。业务逻辑保留给我写，但不能省略关键衔接。
4. 我说“开始”“继续”“按原项目”表示直接提供当前任务尚未完成部分的完整指导，不表示授权代写、覆盖文件或安装依赖。已经讲过的内容简要引用，不重复从头讲。我明确要求“直接修改文件”“帮我实现”或“给完整代码”时，按指定范围执行；直接实现时连续完成必要的编码、检查和修正，不在常规步骤间反复确认。给完整代码不等于授权写入文件。
5. 不强制让我先说方案、回答问题或逐步确认。先解释需求和原项目做法，再给完整指导；我说“我来试”时再留给我独立设计。普通实现细节按现有约定处理；只有影响功能范围、架构、接口契约或缺少必要信息时才集中提问。
6. 我说“检查”或“看看粘贴有没有问题”，先读当前实现，集中指出本任务范围内的问题、位置、原因和最小改法，不只检查一个问题就结束；默认不替我修改，不从旧对话猜代码状态。
7. 默认以 task.md 中的一个任务为本次交付单位，一次覆盖原理、文件分工、实现顺序、关键代码和验收。分步骤是为了理解和编写，不代表必须分轮对话，不要求我反复说“继续”。不顺手重构，不提前实现其他任务或建无关目录、表、空包。
8. 依赖先说明名称、用途、版本，由我安装；不自行执行下载或升级命令。
9. 不熟悉的技术先解释用途与最小概念，关键代码用 `// 【未学】` 标注并给搜索关键词。已知我熟悉 Go、MySQL、Gin 与前端基础；其他熟练程度不擅自假定。
10. 不确定、未实现、简化项和原项目差异直接说清。不能把握手成功当鉴权成功，不能把测试通过当实机通过。

## 3. 每次任务指导的组织方式

一次回答按下面顺序覆盖当前任务；同一概念只解释一次，多个文件围绕业务调用链一起讲，不逐文件重复背景。

```text
【任务目标】完成后有哪些可观察的行为，哪些属于后续任务
【原项目做法】相关文件、调用链、关键设计、本项目的简化和差异
【整体流程与文件分工】请求或消息如何流转；需要新增、修改哪些文件，各自负责什么
【实现步骤】按依赖顺序：文件绝对路径与位置 → 要做什么 → 为什么 → 伪代码或关键片段
步骤之间的调用和数据传递必须讲清楚，覆盖任务所需步骤，不在第一步结束后等待“继续”
【未学技术】结合当前实现解释概念、用途、关键代码和搜索关键词，没有则省略
【验收】启动与请求方法、成功和失败的预期、常见错误；区分自动检查和需要用户实际操作的内容
```

生成的 Protobuf 等机械代码说明来源与生成方式，不要求手写；业务实现按用户授权范围提供。后续需要页面时，同一个功能后端跑通后紧接联调，不攒到全部后端结束。

## 4. 权限与文档职责

- 源码、运行配置：默认只读，除非我明确授权修改。提供片段不等于允许落盘。
- 本文件、框架.md、api.md：默认只读；需要变更先说明，得到明确要求后再改。补接口字段也遵守此规则。
- task.md：可维护当前任务状态和顶部计数；未验收不标完成。不自行增删、重排任务，不追加每轮总结或长篇历史。
- 原项目绝不修改。敏感配置、Token、上传文件和构建产物不进提交。
- 不自行提交、推送或执行破坏性 Git 操作。

## 5. 任务与验收

- 从 task.md 第一项未完成任务开始，不跳行；默认一次只围绕一个任务，完整覆盖实现和验收指导。
- 只有我主动要求慢讲、独立尝试或出现真实阻塞时，才暂停在中间步骤。大任务先给完整路线，再按模块展开；若单次回答确实无法容纳，明确已覆盖和剩余内容，不能只交付一个零散片段。
- 指导已经给全不代表功能完成；不能因为一次交付的目标而省略失败路径和必要验收。
- 只在代码实际存在且约定验收通过后标完成。未运行、失败、待实机验证分别说明。
- 功能完成不等于已经掌握；复盘按需进行，不用额外考试阻塞进度。
- 不为凑进度虚报结果，不为凑工程量添加无关测试。

## 6. 回答结尾

简要说明本次覆盖内容、真实验证状态、仍需我编写或运行的内容、关键业务逻辑或易错点，以及我接下来可以直接做什么。

不机械重复全文，不在已经给出完整任务指导后，再把下一步写成等待讲解下一个小步骤。纯解释或讨论直接回答问题，不硬套任务交付格式。

总结留在聊天，不写入任务清单。

## 7. 新会话与简短指令

新会话先读本文件、任务清单当前项和相关源码，确认实际进度后开始，不照搬过时的进度描述；按需查架构与接口约定。

- “继续”：接着当前任务，完整覆盖尚未讲解或处理的部分。
- “按原项目”：查原作者相关实现后，给出完整任务指导，不先要求我答题。
- “解释”：解释当前问题，不自动展开新任务。
- “慢一点／一步一步”：切换为小步指导，按我的节奏暂停。
- “我来试”：让我先独立写，再检查。
- “检查”：集中检查当前实现，指出问题，默认不修改。
- “直接修改文件”：在指定范围内完成修改和必要验证。
- “完整代码”：提供指定范围的完整代码；是否写入文件按我的明确要求执行。

# IM 框架约束

> 本文件冻结本仓库的架构边界。模块职责、进程入口、消息链路和存储职责以本文为准。
> 改这些边界之前，必须先改本文并得到同意。接口路径以 `doc/api.md` 为准，任务顺序以 `doc/task.md` 为准。
> 事实来自本地参考仓库 `F:\github_IM\im-server` 的 `docs/architecture_zh.md`、`launcher/main.go` 和各模块 `starter.go`。社区版按单进程理解。

## 文档使用方式

本文只管目标架构、模块职责和数据流；协作方式看 `project_ai - 副本.md`，施工顺序看 `task.md`，入口和字段看 `api.md`。列出的全部模块是最终范围，不是当前轮需要建立的目录。

原项目只读。每次只查当前任务相关文件，先解释原作者做法，再一次完整指导用户完成当前任务；任务内可按步骤组织，不要求逐步分轮确认，不按本文一次生成所有任务的模块。当前代码是否具备某能力，以源码与验收为准。

## 1. 目标与非目标

做一个可私有化部署的 IM 后端，学习原项目的模块划分和调用方式。

- 租户用 `app_key` 贯穿 API、RPC、存储和投递。
- 客户端长连接与服务端管理 API 分开。
- 同一用户、群或会话的有状态操作，按方法名和目标 ID 走到稳定处理路径。
- 领域模块通过 Actor 方法名通信，不直接引用其他模块的内部实现。跨模块查询和投递放在公共层。

以下内容不是本仓库当前要宣称已经具备的能力：

- 多节点发现、故障转移和水平扩容。参考仓库里的 `gmicro.Cluster` 在社区版只解析到当前进程。
- 默认端到端加密。传输加密要靠部署时的 HTTPS / WSS。
- Redis、RabbitMQ。参考仓库社区版没有把它们作为直接依赖。未经单独同意，不引入。

## 2. 进程入口

单个 Go 进程开放多个监听端口，共享同一套配置和生命周期。端口可配置，默认值与原项目一致。

| 入口 | 默认地址 | 使用方 | 职责 | 学习顺序 |
| --- | --- | --- | --- | --- |
| Server API | HTTP `:9001`，前缀 `/apigateway` | 业务后端 | 用户、群、消息、会话、历史等服务端 API，签名鉴权 | 主线 |
| Navigator | HTTP `:9002` | 客户端 | 校验 Token，返回 WebSocket 地址 | 主线，先放在同一进程 |
| Connect Manager | WebSocket `:9003`，路径 `/im` | 客户端 | 长连接、Protobuf `ImWebsocketMsg`、上下行消息、ACK、心跳 | 主线 |
| Admin Gateway | HTTP `:8090` | 管理员 | 管理后台页面和管理 API | 后置 |
| Diagnostics | HTTP `:6060` | 运维 | Go `pprof` | 后置 |

启动顺序对齐原项目，做到哪一步实现哪一步：

1. 加载 yaml 配置并初始化日志。
2. 连接 MySQL，并走数据库升级，而不是手改已上线的表。
3. 创建 Actor 运行时，注册各模块方法名。
4. 启动 HTTP、WebSocket 和已实现的后台逻辑。
5. 收到退出信号后关闭。

可选步骤后置：本地 LevelDB（`kvdb.isOpen`）、MongoDB（`msgStoreEngine: mongo`）。默认消息存储用 MySQL。

## 3. 运行时

内部调用使用统一 RPC 信封，至少保留：租户 `app_key`、请求者、目标 ID、方法名、QoS、序号、消息负载。

运行时需要支持四类调用：

- **同步单播**：带超时的请求 / 响应。
- **异步单播**：命令和消息投递。
- **分组路由**：按目标 ID 分批。
- **广播**：把事件发给符合条件的 Actor。

社区版一律解析到当前进程。类名里的 Cluster 不表示已经能多机部署。

新增领域能力时：

1. 在 `services/<name>` 里保持 Actor、Service、Storage 三层。
2. 在该模块 `starter.go` 注册方法名。
3. 由启动入口加载这个 Starter。
4. 用同步调用、异步调用、分组路由或广播，不 import 其他模块的内部包。
5. 表结构变更走统一升级入口。

目录只在对应任务开始时创建，不提前铺空包。

`usermanager` 和 `statussubscriptions` 都注册了 `qry_user_status`。原项目先加载 `usermanager`，后加载 `statussubscriptions`。实现状态订阅之前，先读注册函数，确认同名方法是覆盖还是共存，再决定调用落到哪一个。不提前改名。

## 4. 模块职责

| 层级 | 模块 | 职责 |
| --- | --- | --- |
| 接入 | `apigateway`、`navigator`、`connectmanager`、`admingateway` | REST、连接发现、WebSocket 会话、管理后台 |
| 消息 | `message`、`broadcast`、`botmsg` | 私聊、系统消息、分发、广播、ACK、发送箱、机器人消息 |
| 身份关系 | `usermanager`、`friendmanager`、`statussubscriptions` | 用户、设置、好友、在线状态、封禁、拉黑、状态订阅 |
| 会话 | `conversation`、`group`、`historymsg` | 会话、未读、标签、群、成员、历史、撤回、已读 |
| 扩展 | `pushmanager`、`fileplugin`、`subscriptions`、`rtcroom`、`sensitivemanager`、`logmanager` | 离线推送、文件凭证、事件订阅、RTC 信令、敏感词、可视化日志 |
| 公共与运行时 | `commons` 下的 Actor 运行时、基础上下文、启动器 | 生命周期、路由、RPC 信封、回调 |
| 数据 | MySQL 必须；MongoDB、LevelDB 可选 | 应用元数据、关系和默认消息在 MySQL |

各模块已注册的方法名见第 7 节。HTTP 与这些方法的对应关系见 `doc/api.md`。

## 5. 必须保住的两条链路

### 5.1 私聊

1. 客户端经 WebSocket 发布消息；服务端 API 发私聊时，先进入 `upstream`，真实方法是 `p_msg`。
2. 私聊 Actor 检查租户、拦截、黑名单和好友策略。
3. 保存发送箱和历史。
4. 接收方在线则下发；不在线则走离线推送（推送通道后置，前期至少保证落库）。
5. 给发送方回发布 ACK，带消息 ID、序号和时间戳。

服务端 `POST /apigateway/messages/private/send` 调用 `AsyncPrivateMsgOverUpstream`，内部方法名是 `p_msg`，外层先到 `upstream`。

### 5.2 群聊

1. 按群 ID 路由到 `g_msg`。服务端 API 同样先经 `upstream`。
2. 群模块检查群是否存在、发送者是否成员，并应用禁言、白名单和拦截。
3. 保存群历史和发送箱状态。
4. 按成员扇出。在线下发；离线推送后置。
5. 给发送方回 ACK。

系统消息走 `s_msg`。导入历史时，私聊方法名是 `imp_pri_msg`，群是 `imp_grp_msg`。

## 6. 数据与安全

| 依赖 | 是否必须 | 职责 |
| --- | --- | --- |
| MySQL 8 | 是 | 应用、密钥、用户、群、关系、会话、配置，以及默认消息和历史 |
| MongoDB | 否 | 仅当 `msgStoreEngine: mongo` 时承接部分消息负载 |
| LevelDB | 否 | 仅当打开本地 KV 时保存内部时间序列数据 |
| 对象存储 | 按功能 | 附件和上传凭证 |
| 推送通道 | 按功能 | APNs、FCM 和厂商推送 |

- `app_secret` 只放在可信业务后端和服务器配置中，不进客户端，不进仓库。
- 客户端使用租户范围内的 Token。Navigator 用请求头 `x-appkey`、`x-token` 校验。
- 管理后台、诊断端口、数据库端口不直接暴露到公网。
- 敏感配置来自运行配置，不写进代码和提交记录。

## 8. 实现时的明确差异

学习实现与原仓库保持同一套模块名、方法名和链路。差异只允许这些，并且要写在对应任务里：

- 先实现单进程。分组路由和广播可以先在本进程内完成。
- MongoDB、LevelDB、对象存储、厂商推送、管理后台、RTC、机器人、敏感词、广播，按 `doc/task.md` 后置，不从框架里删掉。
- 推送未实现时，离线用户的消息必须仍然落库，不能假装已经推送到手机。
- 字段级请求和响应在做该接口时对照原 handler 补进 `doc/api.md`，不在实现时临时改路径或方法名。
